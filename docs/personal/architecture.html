架构设计

分几层、每层负责什么、数据往哪里流、哪些条件必须始终成立。不含表结构，不含代码。

第二份，共三份　·　2026 年 11 月

一结构

四层与三个存储面。

入口　人的话 / 订阅事件　→　中心　身份、订阅、投递、合并　→　协调　Last Order 会话　→　执行　实例会话
　　　　　　　　　　　　　↕　　　　　　　　　　　　　　　　　　　↕
配置与状态（数据库）　　历史（按实例）　　产物（按项目）

入口不解释内容，只把输入交给中心。中心只负责投递，不解释内容。协调层只通过管理工具读写配置与卡片，不接触文件与命令。执行层按卡片执行，写产物与历史。

二每层的职责与边界

层负责不负责
入口把人的输入与订阅事件交给中心不判断内容，不拆分任务
中心身份校验、订阅匹配、投递、合并、重投、去重不理解任务、卡片、角色；不保存业务语义
协调理解要求、写卡片、管理模板与实例、管理订阅、与人通信不改文件、不执行命令、不编排执行细节
执行在实例会话中完成卡片、写产物、写历史不改配置、不建卡片、不建实例

三数据流向

  • 人 → 中心 → 协调会话。
  • 事件 → 中心 → 命中订阅的目标（实例或协调会话）。
  • 协调 → 管理工具 → 数据库：模板版本、实例、请求、卡片、依赖、订阅。
  • 卡片 → 执行层 → 实例会话 → 工作区与历史。
  • 实例与协调 → 中心 → 目标。
  • 状态查询 → 数据库 → 面板与命令行展示。

中心不保存任务状态；数据库不保存投递队列；历史库不保存配置；工作区不保存状态。

四单一写入者

每一项数据只有一个写入者，避免两处修改同一事实。

数据写入者读取者
模板版本协调层的管理工具协调、执行装配、面板
实例协调层的管理工具执行层、中心（投递目标）
请求与卡片与依赖协调层的管理工具执行层、面板
订阅卡片生命周期；协调层管理协调自身的订阅中心
执行状态与会话指针执行层协调、面板
历史执行层执行层、检索
产物执行层人、协调、验证

五必须始终成立的条件

  1. 每个实例必须依附一个模板版本，实例本身不带配置覆盖。
  2. 一张卡片在执行期只绑定一个实例；一个实例在同一时刻只服务一张卡片。
  3. 只有协调层能创建模板版本、实例与卡片。
  4. 协调层没有修改文件与执行命令的工具。
  5. 模板决定能力：工具、技能、模型。卡片决定范围：文件路径、禁止命令。两者互不约束。
  6. 消息是单向的，中心不解释内容；回复是另一条消息。
  7. 卡片的订阅随卡片结束删除；协调自身的订阅随其实例存在。
  8. 历史无损；进入模型窗口的是选入的内容与层级摘要，不是截断后的唯一副本。
  9. 产物属于项目，不属于实例；删除实例不删除产物。

六与现有实现的关系

保留：会话引擎、工具框架、技能装载、文档索引、研究流程、面板与命令行、事件记录表。

替换：请求与卡片的存储方式、派工入口、协调层的提示与工具面。

删除：以卡片文件为权威的读写路径、旧派工工具、把验收或等待写进状态机的部分。

本分支不追上游。上游的改动不进入本分支，避免把长期支线的结构绑在别人的节奏上。

七取舍与理由

选择理由代价
不做编排引擎拆分、监督、验收属于提示与模型能力，写进机制会被固定成一种方法质量依赖提示与模型，系统不提供保证
不做多层权限模板管能力、卡片管范围，各自表达一件事，简单且够用没有形式化的越权证明，依赖工具清单与路径检查
中心独立复用投递是通用问题，已有实现，避免自建协议与运维依赖外部包的版本与部署方式
单一数据库配置与状态同源，避免文件与数据库两份事实并发写依赖数据库的事务与锁
实例不带覆盖任何配置差异都成为版本节点，运行可复现小的差异也要产生版本，版本树会长
消息单向不引入请求应答状态，实现简单，失败面小调用方自行判断何时需要后续消息

八失败与边界

  • 中心不可用：本地动作照常，消息在发送端暂存，恢复后重投，按编号去重。
  • 实例异常终止：产生记录，卡片可绑定另一个实例重新开始。
  • 协调会话过长：更换会话，状态从数据库读取，历史保留。
  • 数据库为单机文件：多机部署需要替换存储层，本版本不提供。
  • 中心为单节点：多用户需要多个中心实例，本版本不提供共享。

九部署形态

单机形态：会话与中心在同一台机器，中心走本地 socket 或本机 HTTP。

专机形态：中心单独部署，本机通过 HTTP 连接，需要加密与凭据管理；中心默认只监听本机，对外部署必须前置加密。
